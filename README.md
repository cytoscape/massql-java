# massql-java

A pure-Java implementation of [MassQL](https://github.com/mwang87/MassQueryLanguage)'s `scaninfo`
queries, verified bug-for-bug against the reference Python implementation at a pinned commit.

Reads `.mgf`, `.mzML` and `.mzXML`. No Python, no network, no logging framework — an ordinary jar
that runs anywhere a JVM does.

```
QUERY scaninfo(MS2DATA) WHERE MS2PREC=810.79:TOLERANCEMZ=1.0
```

---

## Two artifacts

They are **versioned and released independently**, and kept deliberately separate.

### 📚 [`massql-java`](docs/SDK.md) — the SDK

The library. Embed it in any JVM application.

A thin jar with a **0.749 MB** dependency closure, enforced by the build. Writes to no stream, logs
nothing, and returns diagnostics as values so the host decides what to do with them.

→ **[docs/SDK.md](docs/SDK.md)** for coordinates and building. **Class-level documentation is the
published `-javadoc.jar`**, not prose in this repository.

### 🖥 [`massql-java-cli`](docs/CLI.md) — the command-line tool

A standalone uber-jar. Spectra file in, JSON on stdout, exit code that means something. The query can
come from a file, from stdin, or inline as `--query`.

→ **[docs/CLI.md](docs/CLI.md)** for arguments, streams, output modes and exit codes, plus
**runnable examples** against fixtures committed to this repository — paste them as written.

> The separation is not cosmetic. The CLI treats stdout as a data pipe; the SDK writes to no stream
> at all. Conflating the two is how a library ends up printing into someone else's application, so
> the docs keep them apart as firmly as the build does.

## Building

The `Makefile` is the only entry point, so what you run locally and what CI runs cannot drift.

```sh
make            # list every target
make build      # both jars
make verify     # the full gate: tests, coverage, lint, dependency audit, spec audit
```

JDK 17.

## How it is verified

Results are compared against goldens generated by the reference Python implementation at a pinned
commit, across all three formats. Underneath that, the three readers are asserted to decode
**bit-identically** to MassQL's own loader — SHA-256 over each peak array, no tolerance — so a
decoding error is caught where it happens rather than surfacing later as a handful of odd rows.

`make verify` runs all of it, plus a 90% coverage gate, an audit that fails if the dependency closure
grows, and a per-format table of every differential pair with its verdict.

# For a reviewer

Everything below is what the review gate is for. Start here.

## What "MassQL parity" means here — and what it does not

⚠ **This is the MassQL `scaninfo` subset, not MassQL.**

Parity means **bug-for-bug agreement with one commit**:

```
dad2a28c01e6e5132240270fc6700fbae29f1652   (tag 2026.03.14)
```

That SHA *is* the definition of "MassQL-compliant" in this repository. Where the reference does
something surprising, we reproduce it rather than improve on it — the goal is that a user swapping
implementations gets the same answers, including the odd ones.

The reference is not a stable target to be precise about: its own documentation advertises functions
that **do not exist** (`scanmaxmz`, `scanrun`), while `scanmz` and `OTHERSCAN` exist **undocumented**.
Claiming "full MassQL parity" would invite a consumer to assume features that reject.

**What parses, executes and rejects is published, not described:**
[`docs/FEATURE_MATRIX.md`](docs/FEATURE_MATRIX.md) — generated from the code, so it cannot drift.

## Known deviations — read these before filing a bug

Six deliberate divergences. Each is a decision, not an oversight.

1. **`ms1scan` is inferred by document order, not read from the file.** MassQL ignores `spectrumRef`
   (mzML) and `precursorScanNum` (mzXML); we reproduce that to match its answers. On interleaved
   acquisition, or where a precursor reference points further back than the immediately preceding MS1
   scan, our `ms1scan` will disagree with the file's declared linkage. For simple DDA they coincide.
2. **`=` means `>=` for intensity comparisons** — MassQL's historical semantics, reproduced.
3. **`i_norm` and `i_norm_ms1` are dropped** from the output as structurally constant.
4. **`tic` is not bit-identical to MassQL's — and ours is the more accurate value.** MassQL's intensity
   column is `float32` and `tic` is a pandas sum over it; we accumulate in float64. Worst measured
   divergence **4.700e-8** relative, compared at 1e-6. ⚠ **The error is in the reference, not in us** —
   a tolerance normally implies the opposite. Every other intensity column is bit-identical, because
   they are selections rather than sums.
5. **`POLARITY` on an MGF filters a constant, not the data.** MassQL hardcodes MGF polarity to 1, so
   `POLARITY=Positive` matches every MGF scan and `POLARITY=Negative` matches none, whatever the
   spectra actually are. Nothing in the output reveals this, which is why it is listed.
6. **Output JSON is compact; the reference emits `indent=2`.** Values are identical and round-trip
   exactly, but the two are **not byte-comparable** — compare parsed values, not `diff`.

## The result contract

**One shape**, twelve keys, for both `MS1DATA` and `MS2DATA`, discriminated by `mslevel`, with no key
ever absent. The single definition is [`docs/RESULT_SCHEMA.md`](docs/RESULT_SCHEMA.md) and it is
machine-checked against every golden.

Per-format population — the same query fills different columns depending on what the format carries:

| Column | mzML | mzXML | MGF |
|---|---|---|---|
| `scan`, `rt`, `tic`, `mslevel`, `base_peak_i`, `base_peak_mz` | populated | populated | populated |
| `precmz` | populated | populated | populated |
| `ms1scan`, `ms1_i`, `ms1_precmz`, `ms1_base_peak_i` | populated | populated | **null** — MGF carries no MS1 survey scans |
| `charge` | file-dependent | **null** where no `precursorCharge` | **never null** — an absent `CHARGE=` defaults to 1 |

That `charge` row is the one most likely to look like a bug: the same experiment as mzXML and MGF
genuinely disagrees, and correctly so.

## Which rules are pinned by which test

The 90% coverage gate is a floor, not evidence. This is the evidence — every claim in
[`SPIKE.md`](docs/harness/SPIKE.md) §3's contract, and the test that holds it:

| Claim | Pinned by |
|---|---|
| 7 columns come from MassQL natively (`scan`, `precmz`, `ms1scan`, `rt`, `charge`, `tic`, `mslevel`) | `DifferentialIT` — 16 pairs, per column |
| `base_peak_i` / `base_peak_mz` are computed per scan (argmax over MS2 peaks) | `ScaninfoCollationTest`, `ReductionsTest`, `DifferentialIT` |
| `ms1_i` / `ms1_precmz` / `ms1_base_peak_i` come from the precursor lookup in the linked MS1 scan | `PrecursorLookupTest`, `DifferentialIT` |
| `ms1_base_peak_i` **survives** a tolerance miss while `ms1_i` goes null | `PrecursorLookupTest`, `CliContractIT` (0.001 ppm) |
| `i_norm` / `i_norm_ms1` are dropped | `ResultSchemaContractTest` |
| One 12-key union shape, no key ever absent | `ResultSchemaContractTest`, `GoldenResultsTest`, spec-audit check 6 |
| Condition windows are **exclusive**; the precursor lookup is **inclusive** | `MzWindowTest`, `PrecursorLookupTest`, and both halves end-to-end in `DifferentialIT` (`micro_mzml_edge`, `micro_onbound`) |
| Readers decode bit-identically to MassQL's loader | `ReaderParityIT` — SHA-256 per peak array, 16 fixtures |
| Two formats of the same data agree | `CrossFormatEquivalenceIT` |
| The CLI keeps stdout and stderr apart in a real process | `CliContractIT` (forks the uber-jar) |

## The eight spike questions

Full answers with evidence: **[`docs/SPIKE_ANSWERS.md`](docs/SPIKE_ANSWERS.md)**. In one line each:

| # | Question | Verdict |
|---|---|---|
| 1 | Bit-identical decoded intensities vs Python? | **Yes** — SHA-256 per array, 16 fixtures, no tolerance |
| 2 | Same rows on `small.mzML` and `small.mzXML`? | **Yes** — 11 of 12 columns bit-identical; `ms1_precmz` ≤ 2.929e-8 (float32 mzXML) |
| 3 | Closure under ~1.5 MB? | **Yes — 0.749 MB, 49.9%.** Two artifacts; the plain javolution fork is not shipped |
| 4 | Is the licence shippable? | **Yes — EPL-1.0 elected.** MSDK is not a dependency; only its decode layer is vendored |
| 5 | Parser choice? | **ANTLR 4.13.2 embedded**, 326,307 B — never the remote `/parse` |
| 6 | Measured LOC vs the 1,200–1,800 estimate? | ⚠ **Missed — 3,162 production lines, 1.8–2.6×.** Hand-written readers account for most of it |
| 7 | Where does it live and how is it published? | GitHub → the NRNB Nexus; two coordinates, three artifacts each |
| 8 | Wall-clock and heap vs pandas? | **6.8× faster, 2.3× less memory** — 0.42 s / 288.5 MB vs 2.84 s / 669.8 MB |

## Licensing and vendored code

**EPL-1.0 is elected** where MSDK's dual LGPL-2.1 / EPL-1.0 applies. Only
MSDK's *decode layer* is vendored — its parser could not be, so the three readers are hand-written.
Per-file provenance a redistributor needs: [`docs/VENDORED.md`](docs/VENDORED.md), asserted on disk by
`VendoredProvenanceTest`.

## Reviewing it yourself

```sh
make fixtures   # two large Ewing files are not committed
make verify     # everything, ending in the per-format differential table
make report     # just the verdicts from the parity and differential reports
```

`make verify` exits non-zero if any pair fails, if any test is skipped, if coverage drops below 90%, if
the dependency closure grows past budget, or if the specs stop describing the code.
