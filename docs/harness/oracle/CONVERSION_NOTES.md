## ⛔ msconvert cannot run on this machine — `small.mzXML` is generated instead

Tech_Step2 §1 and SPIKE.md §6c prescribe ProteoWizard `msconvert` via Docker, calling it "the standard
macOS route". **That is impossible on Apple Silicon.** The image is `linux/amd64`, so it runs under qemu,
and wine's 32-bit code aborts immediately:

```
wine: dlls/ntdll/unix/virtual.c:260: anon_mmap_fixed:
      Assertion `!((UINT_PTR)start & host_page_mask)' failed.
qemu: uncaught target signal 6 (Aborted) - core dumped
```

macOS on arm64 uses 16 KB pages; wine assumes 4 KB. No flag fixes it, ProteoWizard has no native macOS
build, and no alternative converter exists on the host. Note `docker run` still **exits 0** after the core
dump, so a script that only checks the exit code will believe it succeeded — check for the output file.

`oracle/mzml_to_mzxml.py` generates the fixture instead. Its full rationale is in the module docstring; the
two decisions that matter downstream:

**`precision="32"`, not 64.** mzXML has a *single* `precision` attribute for the interleaved m/z-intensity
pairs, so it cannot carry mzML's mixed float64-m/z + float32-intensity. Both options were measured against
the mzML golden:

| | result |
|---|---|
| `precision="64"` | **`tic` differs** (586278.8533592224 vs 586278.875) — intensities decode as float64 so the per-scan sum accumulates in float64 |
| `precision="32"` | `tic`, `base_peak_i`, `base_peak_mz`, `precmz`, `rt`, `scan`, `charge`, `mslevel` all **bit-identical** |

The reasoning inverts the intuition twice: it is the *intensity* dtype (not m/z) that drives `tic`, and the
m/z truncation is harmless for every column in the contract because `precmz` comes from the
`<precursorMz>` **element text**, never the binary array, and this file's base-peak m/z values happen to be
float32-exact. 32 also matches the Ewing profile and what real msconvert emits for mzXML.

**Verified after conversion**, per Tech_Step2 §1:

| Assertion | Result |
|---|---|
| Spectrum count and level split | ✅ **48 (14 MS1, 34 MS2)** — matches `small.mzML` |
| Scan numbering preserved | ✅ scans 1–48; goldens' `ms1scan` = **2, 9, 16, 23, 36, 43** |
| `precursorScanNum` present | ✅ **34** (one per MS2), mirroring the source's `spectrumRef` |
| Oracle agreement (the real test) | ✅ **11 of 12 columns bit-identical** to the mzML golden |

The single remaining column is `ms1_precmz`, which differs by **exactly a float32 truncation** —
`float32(mzML_value) == our_value` verified for both populated records, relative deltas 4.9e-9 and 2.9e-8.
That is inherent to the format, not a defect: `ms1_precmz` reports a *measured* m/z read from the
32-bit array. **Tech_Step12 Pair A should allow ~1e-7 relative on `ms1_precmz` for 32-bit mzXML and stay
bit-exact on everything else.**

> Because this fixture is authored rather than converted by an independent tool, the meaningful validation
> is the oracle cross-check above: MassQL reading our mzXML agrees with MassQL reading the original mzML.
> That is Java-independent. If a real msconvert-produced file is ever obtained (e.g. from an amd64 CI
> runner), diff it against this one — but note it would face the identical single-precision constraint.

## ⚠ Pair B cannot be a row-identity join — the two Ewing files have disjoint scan ids

Tech_Step12 §2 as originally written said "join on `scan`, compare the intersection". **The intersection is
empty.** Measured: mzXML matches scans `[2, 556, 871]`, MGF matches `[370, 598]`.

Cause, and it is structural:

- The MGF's own header says `COM=Conversion of DP00570_F02.mzXML to mascot generic` — same experiment,
  confirmed.
- `TITLE=DP00570_F02.0003.0003.2` encodes the **original mzXML scan number** (0003) and charge.
- But there is **no `SCANS=`**, so MassQL falls back to the 1-based **block index**
  (`msql_fileloading.py:177`). MGF scan 1 is mzXML scan 3.
- Only **625 blocks** survive against 687 MS2 scans — the header `CHARGE=2+ and 3+` indicates charge-state
  filtering dropped 62.

Pair B's actual purpose — pinning the format distinction — needs no join. Assert the **population pattern**
per file instead: the mzXML populates `ms1scan`/`ms1_*` by document order while the MGF nulls them and
reports `rt` as `0.0`. That is exactly what the two goldens show.

> **Carry this to Tech_Step13's known deviations:** for MGF input without `SCANS=`, MassQL's `scan`
> is a *positional index*, not the instrument scan number — even though the real number sits in `TITLE`. The
> A consumer joining results to its own table on `scan` therefore cannot join MGF-derived results back to
> instrument scan numbers. This is a genuine trap for any such feature.

## Further corrections to SPIKE.md / the specs, found while generating

**Both MGF loaders are live, depending on the file.** `_load_data_mgf` (`:145`) tries pyteomics and falls
back to the manual parser only if it yields zero rows. Measured:

| Fixture | pyteomics rows | Live loader | `scan` dtype | `scan` source |
|---|---|---|---|---|
| `PlusRise.mgf` | **0** | **MANUAL** | **str** (`'3'`) | `SCANS=` (present, 34,513 unique) |
| `DP00570_F02.mgf` | 107,178 | pyteomics | int64 | block index (no `SCANS=`) |
| `micro.mgf` | 7 | pyteomics | int64 | block index |

pyteomics cannot index `PlusRise.mgf` (`IndexedMGF object has an empty index`), so `mgf.read()` yields
nothing and the manual parser takes over. The unified rule Tech_Step6 must implement is unchanged —
**`SCANS=` if present, else 1-based block index** — but note `PlusRise.mgf`'s scan ids arrive as **strings**,
the same class of type inconsistency as the mzXML `ms1scan` issue.

**MassQL loads 21,942 of `PlusRise.mgf`'s 34,513 spectra** (758,544 peak rows). The file genuinely has 34,513
`BEGIN IONS` blocks with 34,513 unique `SCANS=` values, so ~12,571 are dropped by the manual loader. Cause
not chased — the golden reproduces byte-identically, so this is the yardstick. **Tech_Step8 must assert
21,942, not 34,513.**

**MGF `ms1_df` is a synthetic 1-row placeholder, not empty.** For `PlusRise.mgf` it is a single all-zero row
(`i=0, mz=0, scan=1, rt=0, polarity=1`). So `massql_query.py`'s `len(ms1_df) == 0`'s `len(ms1_df) == 0` branch is **never
taken for MGF** — the precursor lookup runs and returns nulls because `ms1scan` is 0 and no MS1 scan 0
exists. Tech_Step6 §1's conclusion (Java should expose an empty MS1 table for MGF) still holds and gives
identical results; only its stated rationale was wrong.

**A bare `<precursorMz>` with no attributes crashes MassQL's mzXML loader.** pyteomics returns a plain
string instead of a dict, and `msql_fileloading.py:450` does
`spectrum["precursorMz"][0]["precursorMz"]` → `TypeError: string indices must be integers`. Real mzXML always
carries `precursorIntensity`, and the micro-fixture now does too. A Java reader reads the element text and is
immune, but should tolerate the no-attribute form.

## Reproducing everything

```
bash scripts/fetch-fixtures.sh      # the two uncommitted downloads + the MSDK edge case
bash oracle/generate-all.sh         # every derived fixture, golden and parity dump; idempotent
bash oracle/reproduce-goldens.sh    # the Tech_Step1 gate
```

`oracle/loader-parity/*.json.gz` (4.7 MB total) is Tech_Step8's input. Per scan it carries `peak_count`, the
intensity sum, **SHA-256 digests of the full m/z and intensity arrays** packed as big-endian IEEE754
doubles, and the first 8 values of each as hex for diagnosis. The digest gives bit-exact verification of
every peak in 64 characters — storing all values as hex strings produced 86 MB and was no more rigorous.
Java reproduces a digest with:

```java
ByteBuffer b = ByteBuffer.allocate(8 * n).order(ByteOrder.BIG_ENDIAN);
for (double v : values) b.putDouble(v);
MessageDigest.getInstance("SHA-256").digest(b.array());
```
